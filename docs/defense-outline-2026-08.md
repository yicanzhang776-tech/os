## 2. 答辩核心叙事

一句话定位：

> 我们没有追求比 xv6 或 rCore 实现更多内核功能，而是把 Rust/RISC-V 操作系统实验变成一条可预测、可运行、可解释、可回放、可比较、可评价和可人工验收的证据化学习链路。

答辩只围绕四个问题展开：

1. 为什么现有 xv6/rCore 教学仍需要新的补充；
2. 我们实际实现了什么；
3. 学生和教师如何使用；
4. 哪些内容是借鉴，哪些是本队增量，如何验证没有夸大。

## 6. 专家问答准备

### 为什么不直接使用 xv6 或 rCore？

回答方向：两者都很成熟，本项目不是替代它们；我们针对学生难以把真实输出、代码位置和知识状态联系起来的问题，增加证据化学习层和教师反馈链路。

### 你们的可视化是不是固定动画？

回答方向：不是。页面读取真实构建和 QEMU 串口，通过 `os-demo.event/v1` 生成时间线；未知事件不会自动点亮知识节点，保存后回放与实时解释共用同一目录。

### AI 会不会直接泄露答案或自动评分？

回答方向：服务端只开放六个白名单工具，禁止 solution、教师指南和评分记录；首次使用需要同意；教师评分保持本地并由人工确认，智能体回答不加分。

### 为什么当前内核功能比 xv6/rCore 少？

回答方向：这是有意识的本科教学裁剪。七个 Lab 先覆盖完整核心知识链，再把多核、抢占、ELF、真实块设备作为进阶实验，避免初学者一次面对过多机制。

### 如何证明不是硬编码 PASS？

回答方向：starter 使用 `-ExpectIncomplete`，solution 使用 Stage 1/2/3 与 QEMU 机制证据；教师评分还要求代码审查、实验报告和口试，PASS 不能自动给满分。

### 评价数据怎样保护？

回答方向：学生预览并主动同意；运行记录使用字段白名单和二次净化；不上传源码、完整日志、令牌或环境变量；教师管理端只绑定本机回环地址。

## 7. 制作与压缩检查

- 视频建议 1080p、H.264、30 fps，码率控制在 2.5-4 Mbps；8 分钟通常可控制在 150-240 MB，需为 PPT/PDF 留空间；
- 如果总包超过 250 MB，优先降低视频码率，不要删除 PPT/PDF；
- PPT 使用 16:9；每页只讲一个结论；
- 所有命令输出、评价数据和账号信息必须脱敏；
- 视频中不要展示访问令牌、邀请码、学生姓名或完整本机路径；
- 打包前分别打开 MP4、PPTX 和 PDF，确认可播放、字体正常、链接无关紧要时也能离线讲解；
- 压缩完成后再次检查文件夹名称与总大小。
